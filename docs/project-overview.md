# ANA 项目总览（开发基线）

> 版本：v0.1 draft
> 状态：概念验证（reference implementation）
> 定位：面向个人 AI 与多 Agent 协作的开放架构/协议探索，而非单一聊天产品或模型服务。

## 1. 一句话定义与命名

**ANA（Agent Network Architecture）旨在定义一层由用户本地掌控的 Agent 运行时与通用协议，使记忆、权限、任务状态、模型选择和工具执行不再被绑定到某一家模型公司。**

模型擅长推理、生成和理解；ANA 本地运行时负责用户身份、长期记忆、授权、安全策略、任务分配与本地工具。ANA 的价值不在于取代 GPT、Claude 或本地模型，而在于让它们能够被一致、安全、可替换地使用。

`Agent Network Architecture` 是 ANA 在本项目中的正式展开。它的设计灵感还包括人工神经网络与生物神经系统/DNA 中“信号、编码、连接和演化”的概念；因此可在白皮书叙事中使用 **Artificial Neural Architecture** 或 **Adaptive Network Architecture** 作为启发性的副标题或隐喻。它们不是第二个官方全称，也不应暗示 ANA 在模拟生物大脑或 DNA。

## 2. 项目目标与非目标

### 目标

1. **模型可替换。** 上层 Agent 面对的是“代码生成”“文档分析”等能力，而不是某个固定厂商的 API。
2. **记忆可迁移。** 用户偏好、语义记忆、技能标签和必要工作流状态能够随用户跨设备、跨模型迁移。
3. **本地拥有控制权。** 任意模型只可提出行动建议，无法绕过本地策略直接读取私密数据、执行命令或修改文件。
4. **接口可标准化。** 用一个足够小的通用任务格式连接既有模型接口，先以适配器验证，再推动多方实现。
5. **可被独立实现。** 规范最终应能由多个团队实现并互操作；不能依赖 ANA 的某个专有服务。

### 非目标（至少在 v0.1）

- 不训练或托管基础大模型。
- 不承诺构建一个功能完整的个人助手产品。
- 不把“ANA Chain”误作加密、隐私保护或通用语义压缩方案。
- 不让模型信任等级替代用户授权与本地安全策略。
- 不在第一版定义复杂的自治多 Agent 社会、代币或区块链机制。

## 3. 核心设计原则

| 原则 | 含义 | 工程后果 |
| --- | --- | --- |
| Memory 不等于模型参数 | 用户经验应脱离模型权重存在 | 使用结构化 `MemoryRecord`，可导入、导出与选择性共享 |
| Local-first authority | 本地运行时是授权与状态的最终裁决者 | Adapter 和模型不能直接执行工具操作 |
| Capability over vendor | 按所需能力选择提供方，而非硬编码厂商 | Router 根据 `code_generation` 等能力匹配 Provider |
| Least privilege | 只传递完成任务所必需的数据与权限 | Memory 使用引用和筛选；秘密不进入普通任务信封 |
| Policy before execution | 输出文本与真实行动是两件事 | 每项 `ProposedAction` 必经本地策略门 |
| Standard before product | 首先证明边界和互操作性 | 以 RFC、最小实现和兼容性测试为主要产出 |

## 4. 逻辑架构

```text
                         用户
                          │
                          ▼
┌──────────────────────────────────────────────────────────┐
│                  ANA Local Runtime（本地权威）             │
│  请求解析 ── Memory Store ── Policy Engine ── Event Log   │
│       │                │                │                 │
│       └──────► Capability Router ◄──────┘                 │
└───────────────────────┬──────────────────────────────────┘
                        │ ANA Envelope / State Event
                        ▼
              ┌────────────────────┐
              │ ANA Chain Layer    │  流变换、codon、状态同步
              └─────────┬──────────┘
                        ▼
              ┌────────────────────┐
              │ Provider Adapter   │  适配边界
              └─────────┬──────────┘
                        ▼
          云端模型 / 本地模型 / 专用 Agent 服务
                        │ ProviderResult + ProposedActions
                        ▼
              ┌────────────────────┐
              │ 本地策略门与执行器  │
              └─────────┬──────────┘
                        ▼
                 沙箱 / 文件 / 其他工具
```

### 组件职责

- **ANA Local Runtime**：整个系统的用户侧控制平面；创建任务、选择要带入的上下文、维护状态和审计记录。
- **Memory Store**：保存模型无关的用户偏好、事实、任务总结、技能标签等；记录都有可移植性等级。
- **ANA Chain Layer**：协议的通信/同步核心，将 canonical event stream 以固定、版本化的 Chain 组织；提供可逆流变换、语义 codon 映射和状态增量同步的共同语义。详见 [ANA Chain Layer](ana-chain.md)。
- **Capability Router**：从声明支持相应能力的 Provider 中选择一个。未来可加入成本、延迟、隐私、可用性、用户偏好与信任评分。
- **Provider Adapter**：将通用 ANA 请求转换为某厂商/本地模型的请求；也将其结果还原为通用格式。它不是执行器。
- **Policy Engine**：评估模型建议的行为，返回允许、需要确认、沙箱执行或拒绝。
- **Executor**：只执行已获策略许可的动作，并产生日志、结果和失败信息。

## 5. 关键数据边界

### 5.1 ANAEnvelope：任务信封

`ANAEnvelope` 是 ANA 内部/跨实现传递的最小任务对象。v0.1 包含：

```json
{
  "version": "0.1",
  "task_id": "uuid",
  "intent": "generate",
  "capabilities": ["code_generation"],
  "input": {"text": "生成 Java Hello World"},
  "context": {"language": "java"},
  "memory_refs": ["mem_xxx"],
  "policy": {"execution_mode": "sandbox_first"}
}
```

- `intent` 表达结果导向动作，例如 `generate`、`analyze`、`plan`。
- `capabilities` 表达最低能力需求，例如 `code_generation`。
- `context` 是可序列化、非秘密的任务提示；不能把密码、令牌等直接放进这里。
- `memory_refs` 仅指向本地记忆；运行时在满足策略的前提下选择实际传递哪些内容。
- `policy` 是调用者的期望模式，不会削弱系统的硬性安全规则。

### 5.2 ProviderResult 与 ProposedAction：建议和执行分离

Provider 的返回值有两类：

1. 给用户/上层 Agent 阅读的输出（文本、结构化结果、产物描述）；
2. 明确列出的 `ProposedAction`（例如“将以下内容写入 `generated/Hello.java`”）。

Provider 永远只**建议**动作。只有本地 Runtime 评估后才可执行。这是 ANA 最重要的安全边界之一。

### 5.3 ANA Chain Layer：通信协议核心

Envelope 描述一项任务，ANA Chain 则描述任务、状态和记忆增量如何在 Agent 节点间作为流传递。它由四部分组成：

1. **Stream transformation**：按固定、版本化的链对 canonical stream 分帧和变换；必要时可逆恢复。
2. **Semantic codon mapping**：把稳定、反复出现的协议概念映射为版本化短标识，减少结构化重复并消除词义歧义。
3. **State synchronization**：以事件和增量同步任务进展、记忆变化与协作状态，而非每轮重新发送完整上下文。
4. **Reversible transformation**：让支持该链的节点可以恢复可审计的 canonical 表示，便于跨实现验证与调试。

因此 ANA 不只是“如何调用模型”，也是“AI 节点如何表达和同步结构化状态”。它不替代 HTTPS、WebSocket、local IPC 等传输，也不能代替加密。完整设计、协议栈、协商与验证标准见 [ANA Chain Layer](ana-chain.md)。

### 5.4 MemoryRecord：可迁移记忆

每条记忆至少包括：标识符、类型、结构化内容、创建时间和可移植性。

```json
{
  "id": "mem_xxx",
  "kind": "preference",
  "content": {"security_priority": "high"},
  "portability": "portable"
}
```

v0.1 的可移植性分层：

- `portable`：跨设备可带走的偏好、语义记忆、技能标签等。
- `device_local`：与特定设备相关的缓存、硬件发现结果、本地路径等，不应原样迁移。
- `ephemeral`：当前任务临时上下文，任务结束后可清除。

## 6. 跨设备 Memory 策略与记忆演化

ANA 不尝试把“一台电脑的完整 Agent 内部状态”不加区分地复制到另一台机器，而是迁移一个可解释的 **Migration Profile**。

| 目标设备情况 | 迁移内容 | 重新获取的内容 |
| --- | --- | --- |
| 能力相近的设备 | Portable memory、偏好、技能、兼容工作流状态 | 系统权限、硬件与本地工具发现 |
| 性能明显较弱的设备 | Identity reference、偏好、语义记忆、技能标签 | 模型缓存、大型本地资源、设备专属状态 |
| 高隐私/受限设备 | 经用户筛选后的最小 portable 集合 | 所有秘密、私有缓存、设备本地记录 |

因此，“保留用户习惯”与“复制模型权重/缓存”被明确区分。真正可迁移的人格与偏好应当可审计、可选择、可删除。

### Memory Evolution Layer（记忆演化层）

长时间使用后，系统不能在每次任务中回读所有原始记录。ANA 应将“保存过的内容”与“当前应携带的理解”分开，形成分层演化：

```text
Raw Memory（原始对话、文件片段、事件）
  → Summary Memory（有来源、可更新的阶段摘要）
  → Semantic Memory（稳定事实、偏好、关系、技能）
  → User Model（经同意形成的、可解释的用户工作偏好模型）
```

- **Raw Memory** 用于追溯与纠错，不应默认全量发送给模型。
- **Summary Memory** 以主题或时间段压缩上下文，必须保留原始来源引用和失效条件。
- **Semantic Memory** 只存适合复用的结论，例如“用户优先安全”“主要使用 Java”。
- **User Model** 是对行为模式的可解释推断，不是不可见的用户画像；用户必须可以检查、纠正、导出和删除。

每次抽象都可能丢失细节，所以它不是 ANA Chain 的可逆部分。系统应保存：输入来源、生成者/模型版本、生成时间、置信度、适用范围与可撤销关系。v0.1 当前只实现 `MemoryRecord` 和 portable 导出；Memory Evolution 是下一阶段的核心设计与实现任务。

## 7. 信任、验证与执行安全

模型的输出不应自动被视为可靠指令。ANA 采用四层思路：

```text
模型输出
  → 结构化建议（ProposedAction）
  → 本地策略评估
  → 可选沙箱/用户确认
  → 正式执行与审计
```

### 初步策略规则

- **低风险、已限定范围的动作**：可自动执行，例如写入 ANA 控制的临时工作区。
- **中风险动作**：默认先在沙箱中验证，例如运行不受信任的构建脚本。
- **高风险动作**：必须显式确认或直接拒绝，例如读取凭据、上传私密数据、越界写文件、不可逆删除。
- **第三方 Provider**：默认保守；用户可形成偏好，但不能放宽硬性红线。
- **官方 Provider**：可以享受更高的默认信任等级，但仍不能绕过上述机制。

当前参考实现只落地了最简单规则：允许写入指定工作区内部的文件，拒绝 `../` 等越界路径；其他动作需确认。真实系统必须替换为更完整的策略语言、沙箱和审计机制。

## 8. Adapter 与标准化路线

### 阶段 1：ANA 维护 Adapter

ANA 用少量 Adapter 对接现有 API。Provider 无需改变模型或基础接口，Adapter 负责：

```text
ANAEnvelope → 厂商请求格式
厂商响应格式 → ProviderResult
```

这一步验证统一任务边界是否有价值。

### 阶段 2：Provider/社区维护 Adapter

一旦格式稳定，模型公司、本地模型社区或独立开发者可维护各自的兼容实现。ANA 的责任是规范、测试向量与兼容性，而非垄断接入。

### 阶段 3：原生兼容

长期目标是 Provider 可原生接受 ANA 的结构化意图、上下文和工具约束，但这不能成为 v0.1 的前提。

标准是否成立的判断标准不是“有一个漂亮 Demo”，而是：**两个以上独立 Runtime 和两个以上独立 Adapter 能在没有私有约定的情况下互操作。**

## 9. ANA Chain 的当前定位

此前提出的 `ANA Chain` 在 v0.1 中被收敛为“可逆表示层”的实验：UTF-8 字节经过一系列有元数据描述的可逆操作，接收端按反序还原。它证明的是编解码机制和测试方式，不证明语义编码优势。

必须明确：

- 它**不是加密**，不得用于保护数据或秘密。
- 它**不是压缩**，没有承诺节省 Token 或带宽。
- 它**不是模型通用语言**，尚未证明能让不同模型更容易理解。

后续是否保留，取决于它能否给互操作、结构化状态同步或高效传输带来可测量收益；若无收益，应从协议核心移除，以免增加接入成本。

## 10. 当前代码与已验证闭环

当前参考实现位于仓库根目录，全部用 Python 标准库实现，没有网络调用或 API Key。

| 路径 | 内容 |
| --- | --- |
| `ana/schema.py` | v0.1 的信封、记忆、模型结果和建议动作数据类型 |
| `ana/memory.py` | 内存存储与 portable Migration Profile 导出 |
| `ana/router.py` | 按能力路由的 Provider 接口 |
| `ana/policy.py` | 本地文件写入边界检查 |
| `ana/executor.py` | 仅执行策略允许动作的执行器 |
| `ana/chain.py` | 可逆 ANA Chain 参考 codec |
| `adapters/mock.py` | 可重复运行的 Java 代码生成模拟 Provider |
| `examples/hello_world.py` | 端到端最小示例 |
| `tests/test_ana.py` | 5 个核心行为测试 |

已验证的 Demo 流程：

```text
“生成 Java Hello World”
  → 创建带 code_generation 能力要求的 Envelope
  → Router 选择 MockCodeProvider
  → Provider 返回 Java 源码和写文件建议
  → LocalPolicy 检查路径是否位于允许工作区
  → Executor 写入允许的文件
```

这证明了责任划分；它尚未证明真实模型接入、长期存储、安全沙箱或多 Agent 协作。

## 11. 下一阶段建议（按优先级）

1. **冻结 v0.1 最小协议。** 先规定 JSON 序列化、字段校验、错误格式与版本兼容规则，避免不同 Adapter 各自理解。
2. **添加真实 Adapter，但保持最小范围。** 首选一个 Provider；凭据由用户在本地提供；Adapter 只做请求/响应转换，绝不直接执行工具。
3. **实现结构化审计事件。** 为任务创建、路由、数据披露、策略决定、执行结果建立可导出的事件记录。
4. **替换内存 Memory Store。** 设计本地持久化、加密保护、检索、删除和导出确认流程；不要先追求复杂向量数据库。
5. **设计策略接口与沙箱接口。** 明确动作分类、用户确认 UI 契约、超时/取消、失败恢复与最小权限令牌。
6. **定义多 Agent 协议前置条件。** 先完成任务 ID、能力声明、结果来源、取消、委派深度和上下文预算等基础语义。
7. **开放 RFC 反馈机制。** 把不确定点写成可讨论的 issue，而不是过早锁进代码。

## 12. 未来多 Agent 协作的最小模型

多 Agent 并不等于让多个模型自由互聊。ANA 应将协作限定为本地 Runtime 可追踪的委派：

```text
Coordinator
  → 创建子任务（任务 ID、能力、预算、最小上下文）
  → Router 选择合适 Provider / Agent
  → 子 Agent 返回结果、证据、建议动作与资源消耗
  → Coordinator 汇总；所有真实动作仍经本地策略门
```

未来协议应至少包含：委派关系、输入来源、结果来源、模型/工具版本、取消信号、权限范围、上下文与费用预算。没有这些内容，“智能调配”会变成无法审计的黑箱。

## 13. 当前开放问题

- `intent` 和 `capabilities` 的词表如何治理、扩展和版本化？
- Memory 在何种条件下可跨设备/跨 Provider 传输？如何获得可理解的用户同意？
- 如何对 Adapter 的信息披露行为进行测试与认证？
- Provider 信任评分是本地私有偏好，还是协议可交换字段？应避免形成错误的“安全保证”。
- 沙箱的最低互操作接口应覆盖文件、命令、网络还是浏览器？
- 多 Agent 的结果如何附带可验证来源和失败原因？
- ANA Chain 是否有可测量、不可替代的价值？

## 14. 开发决策守则

以后增加一个功能前，先问四个问题：

1. 它是否让用户记忆或权限更容易被某一模型厂商锁定？若是，重新设计边界。
2. 模型是否能借此绕过本地策略并直接产生副作用？若是，拒绝或改为 `ProposedAction`。
3. 它是否是互操作的最小必要部分？若否，先作为可选扩展而非核心标准。
4. 是否有独立实现者能根据文档和测试重做它？若否，规范还不够清晰。

ANA 的成功标准不是功能数量，而是让用户对自己的 AI 记忆、权限和工具拥有持续的控制权，同时让模型和 Agent 能在清晰的协议边界内自由替换与协作。
